### Mobile performance (2026-09-09)
- Baseline (Lighthouse 12, mobile, simulated slow 4G): home 43, store 55, product 54, collection 56. Main causes: the Google tag library (150 KB, ~0.8 s main-thread blocking during startup, competing with fonts and covers for bandwidth), web fonts swapping in after first paint (LCP re-candidate and the only layout shift), a session fetch and re-render after hydration, cover scans served at one size, and short cache lifetimes on covers.
- Round one: Google tag deferred to `lazyOnload`; fonts `display: optional` with size-adjusted fallbacks; session DTO rendered into the HTML (`src/lib/auth/session-dto.ts`) so AuthProvider no longer fetches on start; 192/256/384 px cover variants through a next/image loader with honest `sizes` on the hero and product page; `/covers/*` immutable for a year; publisher-chip counts raised from 3.2:1 to 4.9:1 contrast.
- Tried and rejected: `experimental.inlineCss` (Turbopack inlined the stylesheet three times per page: 453 KB HTML / 72 KB gzipped versus a 10 KB cached stylesheet).
- Round one result (Lighthouse mobile): home 43→60, store 55→50 (noise; TBT dominated by the tag), product 54→64, collection 56→61; accessibility 100/100/100/99; CLS 0 everywhere; home FCP 3.1→1.9 s, LCP 6.0→3.5 s.
- Round two: product cards render on the server (`ProductCardView` shared by `ProductCardServer` and the client `ProductCard`; only the two cart buttons hydrate); cover plates are hook-free `<picture>` elements with AVIF + WebP srcsets at 192/256/384/640 px, lazy below the fold, eager + preloaded for the product page LCP image; cards past the first row use `content-visibility: auto`; the Google tag library now loads on first interaction or 3 s after the load event (queue set up immediately; the order confirmation forces an immediate load; `NEXT_PUBLIC_GOOGLE_TAG_EAGER=true` restores startup loading).
- Cover scans are high-entropy halftone art (entropy 7.7 bits): WebP quality 30 only halves a 300 px file and AVIF q50 saves about 27%, so the "compress images" estimate is not achievable without visible loss; right-sizing is what was done.

### IndexNow key `dfc2e1d4b27a4fc58d5ad41e60cd5704` (2026-09-15)
- Requested: key file at `https://www.rarecomicscollectors.com/indexnow/dfc2e1d4b27a4fc58d5ad41e60cd5704.txt` and every submission naming it as `keyLocation`. - Live submissions with that keyLocation were then **rejected**: `api.indexnow.org` and `bing.com/indexnow` both answered `422 InvalidRequestParameters: "One or more URLs are not related to your site verified through the keylocation parameter"` for `/`, `/store` and `/guides`, while a URL under `/indexnow/` was accepted (202). This is the protocol's documented rule (indexnow.org/documentation: a key file at `/catalog/<key>.txt` "can include any URLs starting with …/catalog/ but cannot include URLs starting with …/help/"; Option 1, the root, is "strongly recommended"). A key file under `/indexnow/` can therefore never verify the store or the guides.
- Fix: the same handler (`src/app/indexnow/[file]/route.ts`) also serves the key at the site root, `https://www.rarecomicscollectors.com/dfc2e1d4b27a4fc58d5ad41e60cd5704.txt`, through a `next.config.ts` rewrite (only `[a-zA-Z0-9-]{8,128}.txt` names, and only the configured key answers; `robots.txt` is unaffected). Submissions (`submitIndexNow` in `src/lib/indexnow.ts`, used by the `indexnow_ping` and weekly `indexnow_sync` jobs) post `{ host, key, keyLocation, urlList }` with `keyLocation` = the root file; `INDEXNOW_KEY_LOCATION` forces another absolute URL if ever needed and `INDEXNOW_KEY` still overrides the key. The `/indexnow/…` copy stays live for anything that was pointed at it. The server log records the keyLocation of every batch.
- Verified after deployment: both file locations byte-identical to the key; a real JSON batch (`/`, `/guides`, `/store`) with the root keyLocation accepted by api.indexnow.org, the same batch with the `/indexnow/` keyLocation still 422, and Bing's single-URL GET form with the root keyLocation accepted.
- The single-URL browser form (`https://www.bing.com/indexnow?url=…&key=…`) answers 200 with an empty body, so a browser shows a blank page on success and there is no way to see a failure; Bing also answers 202 (not an error) for a wrong key or a placeholder URL. ### PayPal payments that never became a paid order (2026-09-28)
- Reported: a PayPal payment arrived but no order showed on Admin › Orders. Cause in the code: an order is created as `pending_payment` before the buyer is sent to PayPal, and the **only** place the PayPal order was captured and the order marked paid was the buyer's return leg (`/checkout/return`). If the buyer never came back, the function was cut short between the capture and the database update, or the reservation job ran first, the order stayed unpaid and was cancelled after `commerce.reservationMinutes` (30 min); a `PAYMENT.CAPTURE.COMPLETED` webhook that later found the order cancelled only recorded the money as a "late payment, refund required" on a cancelled order — and the webhook could only find the order through PayPal's `related_ids`, which some capture events omit.
- Fix (`src/lib/payments/reconcile.ts`): `reconcilePayment` asks the gateway what really happened (PayPal: fetch the order and capture it if it is only APPROVED; Stripe: read the intent) and books a success through the normal paid transition. It runs (1) from the PayPal `CHECKOUT.ORDER.APPROVED` / `CHECKOUT.ORDER.COMPLETED` webhooks, so an approved order is captured even when the buyer never returns; (2) from `expireUnpaidOrders`, which now checks the gateway before cancelling any online-payment order; (3) from a new `reconcile_payments` job every 30 minutes over the last 7 days of open PayPal/Stripe payments, including on cancelled orders; (4) from a **Check with PayPal / Stripe** button on the admin order page. Capture events are also matched by our order number (`custom_id`) when PayPal omits the related ids.
- Late money now restores the order: when a payment arrives for a cancelled or failed order and every item is still in stock, the stock is re-reserved and the order becomes `paid` (event `order.restored`, seller ledger credited, confirmation sent); only when the copy was sold to someone else meanwhile does the previous behaviour apply (order stays cancelled, `payment.late`, finance alerted to refund). `maxDuration = 60` on the checkout page, the return route and the PayPal webhook so gateway round-trips are never cut short.
- Verified locally: integration suite 26/26 (new checks: late payment with stock available restores the order, takes the stock back and credits the ledger; with the stock gone it stays cancelled and flagged; expiry still cancels stale test/card reservations and keeps bank-transfer windows), unit 60/60, production build clean.
- Not verifiable from the code: which of the causes hit the reported payment. PayPal's transaction shows the order number in its "Custom" field; searching Admin › Orders for it (all statuses) finds the order — if it is there as cancelled with an open PayPal payment, the half-hourly job (or the button) books it and restores it. The PayPal webhook must be subscribed to `CHECKOUT.ORDER.APPROVED` as well as the `PAYMENT.CAPTURE.*` events, and it is still registered on the old vercel.app host (see section 2).
- Follow-up (2026-09-28, second deploy): the reported order turned out to be exactly the "late payment" case — cancelled by the reservation job, then stamped paid-but-cancelled by the webhook before the restore logic shipped, so nothing re-checked it. `restoreLatePaidOrder` (lifecycle) now takes a cancelled/failed order whose payment is confirmed and unrefunded back to `paid` when every copy is still in stock (stock re-reserved, ledger credited once, confirmation and seller alert sent, event `order.restored`); the half-hourly `reconcile_payments` sweep applies it to the last 7 days and the admin **Check with PayPal** button applies it on demand (it now also shows on paid-but-cancelled orders). Integration suite 29/29.

- **Duplicates:** same source id = an update, never a second row; same certification number as a listing or queue item, or same seller + title + photo = Duplicate; same publisher + title + issue + grade + grader + label/variant = Possible duplicate (may be a second copy; the admin decides). The release step re-checks the certification number.
- **Pricing:** selling price = source price × 1.25 (`src/lib/imports/pricing.ts`; markup editable, stored per item). `sourcePrice`, `markupBps` and `retailPrice` live on `ImportItem` only; the storefront reads `Product.price` and no page, feed or API response carries the source price. On a source price change an untouched price is recalculated; a hand-set price (edited in the queue or on the listing) is kept and flagged unless "Automatic price synchronisation" is on.
- **One-time migration (seed):** all 2,442 queued listings became queue items: those already live are Released, scheduled drafts are Pending Review. Their selling price was set to source × 1.25 on the queue item and on the listing, live listings included; a listing whose price had been changed by hand would have been kept (none locally).
- **Ownership:** imported products are house inventory (`sellerId` null), SKU `IMP-<source id>`; no customer page names the source. Source URL, seller and price appear only in the admin.
- **SEO recommendation per item** (`src/lib/imports/seo.ts`, no paid calls): primary and secondary keywords from the keyword table held by the SEO system (says so when an issue has no search data), search intent, SEO title, meta description, slug, H1, and internal links to the matching collection, publisher, character and issue-guide pages; checks for length, stuffing and a title that contradicts the issue or grade. Edited SEO title/description are used by the product page.
- **Sync:** every upload or feed fetch updates known products (price, availability, title when not yet reviewed and not edited). "Complete catalogue" files/feeds mark missing products unavailable: queued ones leave the flow, released ones are set to sold out; stock is never raised automatically.
- **Admin:** `/admin/imports` (statistics, upload, pricing and sync settings, run log), `/admin/imports/queue` (filters, bulk Approve / Release / Reject / Back to review / Remove), `/admin/imports/[id]` (edit facts, price, SEO; decisions). The old `/admin/release-queue` redirects there.
- Verified: unit tests for pricing, duplicate keys, release checks, SEO rules and source parsing; browser test of upload → queue → approve → edit → release → price sync → sold-out sync; migration checked row by row against the formula.
- Not migrated: the 2,165 rows the first imports held back (they have no stored photo address). Uploading those CSV files again brings them in as Error items that can be completed.

## 3. Known limitations and recommendations (not yet done)
- Mobile Lighthouse performance sits at 69–78 (home 69, store 69, product 78, collection 72 after round three) because of client-side JavaScript (header, cart, currency providers, store browser); trimming hydration is the next lever. Next built-in polyfills (~14 KB) and the Google tag library (unused JS, external) are the remaining flagged items.
- Knowledge base: 107 articles is the first batch; the JSON import at `/admin/guides/import` is the path to the 10,000-article target. Each batch should keep the same rules (documented facts only, one question per article, links to listings and hubs). Candidate next batches: one article per key issue currently in stock, one per publisher and era covered by the catalogue, and a monthly industry-news entry with dated, sourced events.
- The store page ships every published listing to the browser and filters client-side. That is fine at a few hundred listings; the release queue adds 100 a day, so server-side search and pagination for `/store` should land before the catalogue passes roughly 1,000 listings (about ten days into the schedule).
- Release-queue photos live in the repository (`public/covers/q`, 157 MB for 2,442 listings). Setting `BLOB_READ_WRITE_TOKEN` and moving them to Vercel Blob would keep the repository and builds small as more CSV batches arrive.
- Back/forward cache is disabled by `Cache-Control: no-store` on dynamic HTML.
- Product cover art for the first two imports is the issue's cover scan, not photos of the actual slab (the HipComic queue uses the listing photos); sellers should upload real photos from their dashboard.
- Live Stripe/PayPal have not been exercised with a real charge; the `test` provider covers checkout → refund end-to-end.
- No cookie-consent banner yet: EEA/UK/CH visitors are measured cookielessly (Consent Mode default denied) and never get the chance to opt in; add a small banner that calls `gtag(consent,update,…)` if full analytics coverage in Europe is wanted.
